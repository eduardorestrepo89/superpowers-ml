EDA Restraint Study

We tried to make a coding agent run exploratory data analysis on its own with the discipline of a careful senior data scientist. The agent knows the method. It does not hold to it when the request itself is the mistake, and the harness it runs in is not ours to control. The conclusion: EDA with this stack has to be a human-assisted process.

Date 16 Oct 2026Period covered 23 Sep – 29 Sep 2026Agent Claude Code 2.1.284, Opus 5.5, headlessSource sebasr0/ml-skills, branch eda-subsystem @ 4f7934b

1Summary

Conclusion

Autonomous EDA does not work well enough to trust. Skills can teach method, but the agent already has the method; what fails is holding to it against an explicit request, and no skill can outrank the request or seal the paths the harness leaves open.

The agent should propose, interpret and record. A human should drive execution, supply domain facts and sign the readiness verdict. The deterministic runtime stays, as a guard against accidents, not as a substitute for the human.

The evidence comes from a restraint benchmark we built for this purpose and from the incidents we hit while running it. The benchmark measured the agent without EDA skills (the RED baseline in Superpowers' skill-TDD method). A GREEN run with skills was never made, so the claim that skills are not enough is an argument from that baseline and from the harness record, not a measured GREEN failure. Section 9 says how to measure it if that is needed.

2Objective

The project brief set out to turn this Superpowers fork into a methodology-driven data-science agent, starting with EDA. Its thesis:

A good Data Science agent should not merely know how to write pandas/sklearn code. It should operate under methodological restraints that prevent common statistical, data-quality, leakage, validation, and reasoning errors.CONTEXT-PROJECT.md

The brief asked for three separated layers, and the approved design kept them:

  • Skills for judgment: data context, grain, missingness, leakage, anomalies, which diagnostic fits which question.
  • A deterministic runtime for anything mechanically checkable: hashes, uniqueness, join cardinality, splits, holdout protection, the readiness gate.
  • Reference knowledge (a curated NIST/SEMATECH extract) consulted when choosing a diagnostic, never driving the workflow.

On 23 Sep the execution model was set to the agent writes and runs everything; the human reviews results in marimo-pair. This report revisits that decision.

3.2 What was built

The runtime, edakit, is a Python CLI under skills/running-eda/runtime/. It is the part of the design that does not depend on the model complying:

RestraintHow edakit enforces it
Raw data is immutableSHA-256 manifest, read-only file attribute, gate blocks on hash drift
No destructive cleaning during EDAProduces no cleaned dataset; the only derived data are declared joins and splits, with lineage
Joins need declared keys and cardinalityjoin --expect 1:N measures uniqueness, fan-out and orphans, and refuses on contradiction
Grain claims need verificationgrain.verified is set only by a passing check grain
Observations need provenanceOnly runtime commands write OBSERVED evidence; the agent can add INFERRED, HYPOTHESIS and decisions, and only a human can add a DOMAIN_ASSUMPTION
Evidence is append-onlyHash-chained evidence.jsonl; ledger verify detects edits
Holdout protected against accidentWritten outside the workspace; target-aware commands refuse it; reads go to an access log the gate checks
Readiness is computed, then signedgate returns GO / GO_WITH_WARNINGS / BLOCKED; a human signs; the agent never declares "EDA complete"

3.3 The restraint benchmark

The benchmark follows Superpowers' rule for skills: no skill without a failing test first. It records what an agent does with no EDA skill, so each later skill can be written against a real, quoted failure.

  • Tier 1, pressure scenarios (S01–S24). Each prompt asks for a concrete action that is methodologically wrong, wrapped in realistic pressure: a demo in 40 minutes, a manager's rule, a colleague who "always did it this way".
  • Negative controls (N1–N4). Requests that are fine. They catch over-restraint: an agent that refuses or interrogates when it should just do the work.
  • Tier 2, end-to-end EDA (T2-1–T2-5). Open tasks, "do the EDA and tell me whether the data is ready", on datasets with planted problems. T2-5 is also a control.
  • Ten seeded fixtures with documented traps: sensor (−999 sentinels, a unit change, a real heat event), churn_panel (customer × month, a target proxy, an extraction-time feature), loans, orders_customers (fan-out, orphans), subscriptions, purchases, wide (500 features), survey, active_customers, sales. Their bytes are pinned by hash.

3.4 Research inputs that shaped the design

  • NIST pack: useful for the Tukey stance, the four assumptions, the 4-plot and robust estimation. It covers none of leakage, split discipline, grouped or temporal validation, dataset shift or high-dimensional multiplicity, and conflicts with predictive ML if applied blindly (normality tests at ML sample sizes, Grubbs-style deletion, randomness tests on file order). Verdict: a ~900-token curated extract, not the vendored pack.
  • Urika: adopted "the model emits, code decides", a hashed raw-data manifest, a deterministic profiler, and a read-only evaluator at the gate. Skipped per-role permission policies, because its own security notes admit there is no sandbox and once python is allowed a command allowlist is cosmetic. That observation returns in section 6.
  • Modern methodology: split first and fit inside the pipeline; split to match deployment (group, time, gap); leakage as information not available at prediction time; MAR vs MNAR is untestable from observed data; FDR control for screens; inferred schemas are drafts to review.

What the agent already does without any EDA skill

These restraints held in at least 2 of 3 reps with no EDA guidance: keeping a stated holdout out of exploration; spotting target proxies and features unavailable at prediction time; correcting for multiplicity in screens; refusing a causal claim from an association; verifying grain before a rate; checking key cardinality before a join; sampling by entity; not deduplicating without an identifier; refusing to infer MNAR or MCAR from a test. 6Why skills are not enough for autonomous EDA

A Superpowers skill is text loaded into the agent's context. It can add knowledge, name rationalizations and set up a checklist. Seven findings say why that cannot make unattended EDA safe in this setting.

6.1

The agent already knows the method

24 of 33 exercises passed in at least 2 of 3 reps with no EDA skill. In the failing pressure scenarios the same answer usually names the correct method: the group split, the train-only pipeline, the sentinel, the sorted file. A skill's main lever is knowledge, and knowledge is not what is missing.

Evidence. In most comply-then-caveat reps the agent stated the correct method in the same answer; S02 was the exception (RED record §7). S16: 0 of 500 features significant after correction, and one rep advised against the "validated signals" slide.

6.2

A skill ranks below the request

The dominant failure has one shape: the user's explicit instruction is itself the error. Superpowers puts user instructions above skills (User instructions … take precedence over skills, from using-superpowers), and Claude Code is built to follow the person at the keyboard. A skill that says "refuse" is competing with the instruction that has priority. Prohibitions, rationalization tables and red flags, the tools writing-skills prescribes for this failure, can shift the odds. They cannot change the ranking, and we would not want a tool that overrides its user as a matter of design.

Evidence. 22 of 31 failures: S01, S02, S06, S07, S08, S12, S13 at 0/3, and S20 r1. All of these prompts except S20 carried authority or time pressure. In all three S07 reps the agent minimized its own violation in nearly the same words: the effect is probably small, probably tiny, the effect is small.

6.3

Omissions need a required step, and a required step needs a door

When nobody mentioned a holdout, no agent made one before target-aware analysis. "Remember to protect the holdout" is the weakest form of guidance. The reliable form is a step that cannot be skipped: edakit refuses run --target-aware before split. That only works when the analysis goes through edakit, which leads to the next point.

Evidence. T2-4, 0/3: default rates by quintile and 5-fold cross-validation on all 2,000 rows; a time split suggested only at the end. When a holdout was stated (S05), all 3 reps protected it.

6.4

The runtime guards only its own door

EDA needs Python, and once the agent can run Python it can read the holdout, write a cleaned file or fit an imputer with pandas without touching edakit. The spec accepted this openly: holdout protection is accident-proof, not adversary-proof (§3.4), and the PreToolUse hook was postponed. The Urika review reached the same point. Closing the gap needs control of the harness itself: hooks on every command, an OS-level sandbox around the holdout. Hooks see the command line, not what a script does once it runs.

Evidence. The baseline ran without edakit, so it does not test a bypass directly. It does show the tool any bypass would use: the files that proved a flawed action ran (sensor_clean.csv, loans_imputed.csv, subscriptions_reduced.csv, churn_income_imputed.csv; 13 forbidden outputs in 99 runs) came from scripts the agent wrote and ran itself, Python through Bash or PowerShell. Any EDA session has to allow that.

6.5

We do not control the harness

Over one week, eight separate harness-level problems changed what the agent could do or what we could measure (section 7). None of them could be fixed from a skill, and several could not be fixed by us at all: endpoint security and OS housekeeping on a managed PC belong to IT, and the permission matcher, safety classifier and usage limits belong to the product. A methodology that depends on the agent operating unattended inherits all of that variance.

Evidence. The first 62 runs were discarded because 36 of them had calls denied. The work had to move to a second PC because FortiEDR blocked Python writes mid-batch, even after IT reported Claude as unlocked.

6.6

Checking an EDA needs judgment the model does not reliably supply

An LLM judge graded actions well and interpretations less well. Every benchmark defect we found was found by a human reading runs. If a strong model cannot reliably grade an EDA against a written rubric, an autonomous agent cannot be trusted to certify its own.

Evidence. The human audit corrected 2 of 6 S17 grades, both interpretations of the same wording. The first rubric graded "comply, then caveat" as PASS in some scenarios and FAIL in others; making it consistent flipped 11 verdicts. S02's first fixture had no real correlated pair, and T2-5's first prompt was ambiguous; both were caught in human audit.

6.7

More restraint is not free

The obvious skill-side fix is to push restraint harder. The baseline already shows the cost: an agent that doubts a fact the user stated and holds readiness hostage to it. The right balance needs domain facts that only a person can give, which is why the design lets only a human originate a DOMAIN_ASSUMPTION. Some blockers are invisible to code entirely: a corrupted source, a population mismatch, unusable labels.

Evidence. T2-5 r2 made readiness wait on confirming feature timing the prompt had already stated. S18 passed because the agent flagged the active-only sample, a judgment no deterministic check makes.

What changes with a human in the loop. The comply-then-caveat failure becomes a cheap question. When a request conflicts with method, the agent stops before executing and asks; the person is there to answer, often in seconds. The same instruction that fails unattended ("stop and ask") is easy to follow when someone is present, and the agent's knowledge, which section 5 shows is good, does its job as advice.

8Recommended operating model: human-assisted EDA

This reverses the 23 Sep execution decision and returns to the direction running-eda-ml on the fork's main already took on 16 Sep: the human drives execution, the agent drives interpretation. The runtime built since then stays and becomes the shared record both work from.

Run sessions in Claude Code's default permission mode, not acceptEdits or auto mode, and keep python off the allowlist, so any Python the agent runs outside the notebook stops at the approval prompt. That is the one harness checkpoint we do control.

Keep

What we built

  • edakit: hashes, read-only raw data, verified joins and splits, the hash-chained ledger, the computed gate
  • marimo-pair with human-run cells, as in running-eda-ml
  • The benchmark, as a regression suite for any future skill change
Change

Where skill effort goes

  • One discipline, loaded by every EDA step: when the request is the error, stop and ask before executing
  • Make protecting a holdout a required step, not a reminder
  • Deliver inferred schemas and contracts as drafts for review
  • Record a human's stated fact as a DOMAIN_ASSUMPTION and proceed
Drop or postpone

What the evidence does not support

  • Autonomous end-to-end EDA
  • Six separate topic skills: establishing-data-context had no failure at all
  • A PreToolUse holdout hook, until it can see more than the command line

9Limits of the evidence and next steps

  • No GREEN arm. We never ran agents with EDA skills, so "skills are not enough" is inferred from the baseline and the harness record. If a number is wanted, a GREEN run of the 9 scenarios that failed 3 of 3, at 3 reps, is 27 runs, about $4 notional at the rerun's $0.16 per run.
  • One model, one harness version, one week. Opus 5.5 is strong at baseline. Weaker models may fail scenarios this one passed.
  • Three reps per scenario. A rate such as 2/3 is coarse.
  • The fork's existing skills were not measured. The red-fork-main arm (brainstorming-ml and running-eda-ml) was dropped by choice. Whether they help or hurt is unknown.
  • S17's rubric needs tightening before any further grading: it does not say whether "the rows can be treated as independent" counts as a process claim.
  • The human-assisted model itself is not benchmarked. Headless claude -p cannot play the human. Measuring it needs scripted human turns or observed live sessions.
